# Поиск людей PolyLink: требования и план реализации

Дата проверки кода: 25 октября 2026 года.
Статус: реализовано 26 октября 2026 года по отдельному запросу пользователя. Приняты предложенные значения раздела 3; API, ограничения и проверки описаны в [результате реализации](search_implementation.md).
Исходный план ниже сохраняет требования и состояние кода на дату проверки. Реализация меняет сервер и клиент; миграции и наполнение реальных данных не выполняются.

## 1. Согласованные требования

1. Поиск охватывает выпускников и преподавателей (`graduate`, `lecturer`). Закрытость профиля сама по себе не исключает человека из поиска.
2. При выбранных фильтрах образования человек подходит, если существует хотя бы одна запись его образования, в которой одновременно совпадают все выбранные условия: специальность, институт, год выпуска. Нельзя взять специальность из одной записи, а институт или год из другой.
3. Карточка показывает именно совпавшее образование, а не произвольное или сводные поля пользователя.
4. Для закрытого чужого профиля видимы только имя, образование и должность. Кнопка просмотра профиля заблокирована; серверная защита просмотра сохраняется. Открытие чата сохраняется с действующими ограничениями.
5. Серверная пагинация возвращает не более 100 пользователей на страницу. Фильтрация выполняется до пагинации. Несколько образований не создают повторные карточки одного человека.
6. Варианты фильтров загружаются из БД, а не задаются списками в HTML.

Технические идентификаторы и флаги доступа допустимы в минимальном ответе API для работы кнопок; это не разрешение показывать дополнительные сведения о закрытом профиле.

## 2. Проверенное текущее состояние

| Участок | Фактическое поведение и пробел |
| --- | --- |
| `search.html` | Фильтры `faculty`, `year`, `institute` заполнены фиксированными вариантами; заголовок говорит только о выпускниках. Управления страницами нет. |
| `js/search.js` | После авторизации вызывает `search.people` с `q`, `specialization`, `year`, `institute`. Есть debounce 200 мс, защита от устаревшего ответа через generation, состояния загрузки/ошибки/пустого результата. Карточка читает плоские поля пользователя, а не совпавшую запись Education. |

| `js/data/http/routes.js` | `search.people` делает GET `/search`, но передаёт только `q`: остальные параметры теряются. |

| `ChatService.people` | Проверяет длину `q` до 100, экранирует LIKE, выбирает TOP (100) по имени и фамилии; сортировка FirstName, LastName, UserId. Допускает ADMITTED с подтверждённой почтой. Возвращает id, имя/фамилию, роль, onboardingComplete, canOpenProfile; образования и должности нет. Фильтра по роли в SQL нет. |
| `IdentityController.ownProfile` | GET `/users/{userId}` проверяет сессию и доступ: чужой закрытый профиль даёт 404 NOT_FOUND, свой доступен. `jobTitle` читается из `Users.Specialization`; `education` пока возвращается пустым списком. Нельзя считать профильный HTTP API готовым источником образования. |
| `js/data/mock/provider.js` | Ищет по имени, должности и плоской специальности, фильтрует плоские поля; выдаёт минимальный объект без образования/должности. Семантика отличается от HTTP. |
| `js/chat/groups.js` | Выбор участников вызывает тот же `search.people({q})` и ожидает массив. Простая замена ответа на объект страницы сломает этот сценарий. |
| `js/chat/direct-contact.js`, `ChatService.direct` | Сохраняются запрет чата с собой, серверная проверка допуска участников и блокировок; снятие только собственной блокировки требует подтверждения, чужая блокировка не обходится. |

Источники данных проверены по baseline `backend/src/main/resources/db/migration/V1__restored_schema_baseline.sql`: `dbo.Education` содержит EducationId, UserId, UniversityId, DegreeId, SpecializationId, InstituteId, StartDate, EndDate; есть справочники Institutes и Specializations. Это схема репозитория, не аудит содержимого рабочей БД.

Инструкций AGENTS.md в проверенном дереве и родительских каталогах не обнаружено. Текущие ограничения HTTP также описаны в корневом README и `docs/frontend_context.md`.

## 3. Предлагаемые значения по умолчанию

Следующие решения нужны для однозначной реализации, но не выдаются за отдельно согласованные пользователем требования.

| Вопрос | Предложение и основание |
| --- | --- |
| Нет фильтров образования | Показывать всех подходящих по имени допущенных выпускников и преподавателей, включая людей без Education. Так преподаватель без записи образования остаётся доступен. При любом образовательном фильтре запись Education обязательна. |
| Пустой запрос | Пустой `q` означает каталог с выбранными фильтрами; все пустые параметры — первая страница каталога. Не вводить минимальную длину запроса без отдельного требования. |
| Полнотекстовая область | Сохранить серверный поиск подстроки по `FirstName + пробел + LastName`, обрезая края строки. Поиск по должности/образованию, обратный порядок имени и транслитерация — отдельные улучшения; привести mock к выбранному контракту. |
| Год | Календарный год `Education.EndDate`; NULL означает незавершённое/неуказанное образование и не совпадает с выбранным годом. Не использовать год начала или сводный graduationYear пользователя. |
| Несколько совпавших образований | Одна карточка, внутри все совпавшие записи. Основная — EndDate по убыванию, NULL после завершённых, затем EducationId по возрастанию; остальные доступны через раскрытие «ещё N». Не ограничивать список молча. |
| Образование без фильтров | Использовать тот же порядок для всех записей человека. При отсутствии записей показать «Образование не указано». |
| Должность | Для совместимости с текущим профилем использовать `Users.Specialization` как источник `jobTitle`; не смешивать с Education.SpecializationId. Если поле пустое, показать «Должность не указана». Выбор должности из WorkExperience потребует отдельного правила. |
| Размер страницы | 50 по умолчанию, допустимый limit 1–100; выход за диапазон — ошибка валидации. |
| Сортировка людей | Сохранить FirstName ASC, LastName ASC, UserId ASC с явно зафиксированной collation БД. UserId разрывает равенство имён. |
| Свой закрытый профиль | Сохранить существующее исключение владельца для кнопки просмотра; закрытый чужой профиль всегда заблокирован. |
| Справочники | Институты/специальности — id и подписи из таблиц, годы — DISTINCT YEAR(EndDate) по доступному поисковому набору; без NULL. Начальный вариант «Все» остаётся элементом UI. Списки независимы от текущего q, без каскадного ограничения на первом этапе. |

Роль нужна для отбора и совместимости, но отдельный переключатель ролей и отображение роли в закрытой карточке не входят в подтверждённые требования.

## 4. План backend и данных

1. Зафиксировать DTO поиска отдельно от полного профиля: строковые user id, имя, `jobTitle`, `canOpenProfile`, `matchedEducation` (id, учреждение, степень, институт, специальность, даты) и необходимые существующим потребителям служебные поля. Сериализовать по белому списку. Для закрытых карточек не отдавать email, фото, описание, обложку, сертификаты, опыт работы или полную модель аккаунта.
2. Сохранить обязательную сессию и текущие условия допуска ADMITTED/подтверждённой почты; явно ограничить целевые роли graduate/lecturer. Проверить правила жизненного цикла аккаунтов, чтобы удалённые/деактивированные/недопущенные пользователи не появлялись. Поиск не должен раскрывать причины ограничений чата.
3. Реализовать параметризованный запрос: условия пользователя и q плюс один коррелированный `EXISTS` к Education, внутри которого объединены все выбранные образовательные условия через AND. При отсутствии образовательных фильтров EXISTS не нужен согласно предложенному поведению.
4. Сначала получить страницу уникальных пользователей в заданном порядке, затем пакетно выбрать только подходящие образования для id этой страницы, соединяя справочники. Не делать LIMIT/TOP по JOIN-строкам образования и последующую дедупликацию в Java. Избежать запросов по одному пользователю, включая получение роли.
5. Фильтровать институт/специальность по числовым id, а не по подписи. Проверять тип, диапазон года, длину q и корректность курсора. Сохранить экранирование LIKE и привязку параметров. Ошибочные значения не превращать молча в «Все».
6. До реализации сверить фактические связи Education и заполненность данных после регистрации обоих типов пользователей: registry admission не доказывает наличие Education. Не подменять образование данными реестра или плоскими полями Users без отдельного решения. При недостатке данных документировать необходимое наполнение отдельно.
7. По плану выполнения SQL оценить индексы Education по UserId и фильтруемым FK/EndDate. Для года предпочесть диапазон дат вместо YEAR в условии, если это улучшает индексный доступ. Не обещать индексный поиск `%q%`; оценить на реалистичном объёме. Миграция допустима только отдельной реализационной задачей по существующему schema workflow.

## 5. API, пагинация и совместимость

Рекомендуемый контракт новой операции `search.page`:

- GET `/search/people` с `q`, `specializationId`, `instituteId`, `year`, `limit`, `cursor`.
- Ответ `{items: [...], nextCursor: string|null, hasMore: boolean}`. Точный total не нужен для последовательной навигации; не объявлять его требованием.
- Отдельная операция `search.filters`: GET `/search/filters`, ответ `{specializations: [{id,label}], institutes: [{id,label}], years: [число]}`. Она требует обычной сессии, а не enrollment-сессии; существующий enrollment options не подходит как готовая замена.

Названия новых операций/маршрутов — предложение. Предпочтительно сохранить GET `/search` и массив `search.people({q})` для существующего выбора участников, а общий серверный поиск выделить в переиспользуемый сервис. Legacy-операция может возвращать items первой страницы с прежними служебными полями. Новая страница поиска использует `search.page`; групповой поиск нельзя неявно ограничить наличием Education. Отдельно решить, нужна ли его UI пагинация: это расширение текущего выбора участников, не условие внедрения каталога. Не менять одновременно формат существующей операции без миграции всех потребителей.

Предлагается keyset-пагинация по `(FirstName, LastName, UserId)` в той же collation, что ORDER BY. Выбирать limit+1 пользователя для hasMore, возвращать максимум limit. Курсор должен быть непрозрачным для UI, валидироваться сервером и быть связан с нормализованными q/фильтрами/сортировкой, чтобы его нельзя было использовать с другим запросом. При изменении запроса или фильтра начинать с первой страницы.

При неизменных данных проход страниц не пропускает людей и не повторяет их, включая одинаковые имена и несколько образований. Изменение имени, образования или допуска во время обхода может менять состав выдачи: keyset не даёт снимка БД между запросами. По умолчанию достаточно свежего каталога с явным сбросом/обновлением; строгий снимок потребовал бы отдельного механизма. Клиент также может защищаться от повторного добавления id при подгрузке.

## 6. План frontend

1. Добавить маршруты, сервисные операции и отдельные нормализаторы DTO страницы/образования поиска. Убрать локальную фильтрацию HTTP-выборки; не использовать полный normalizeUser для маскировки отсутствующего контракта пустыми строками. Синхронизировать mock по семантике и формату.
2. Удалить фиксированные варианты из search.html, оставить «Все»; загрузить справочники из API, использовать id как value. Обработать ошибку загрузки с повтором; не показывать старые фиктивные списки. Заменить заголовок на нейтральный для выпускников и преподавателей.
3. Сохранить debounce, Enter, кнопку поиска и защиту от устаревших ответов; распространить generation на загрузку страниц. При изменении q/фильтра очищать курсор и предыдущую выдачу. Добавить «Показать ещё» либо следующую страницу, блокируя повторный запрос во время загрузки.
4. Рендерить совпавшие образования из ответа, должность и имя с экранированием текста; корректно показать отсутствующие даты/значения и несколько образований. Не подставлять образование из другой записи.
5. Сохранить disabled и пояснение для закрытого чужого профиля; дополнительно не выполнять переход обработчиком, если действие запрещено. Не считать клиентский флаг заменой серверной проверки: доступ мог измениться после получения карточки.
6. Сохранить `openDirectWithUnblock`, подтверждение снятия своей блокировки и текущие серверные ограничения. Для себя кнопка связи остаётся выключенной; ошибки открытия чата показываются штатным способом.
7. Обеспечить доступные подписи фильтров, клавиатурную навигацию, состояния начальной загрузки, пустой выдачи, конца списка и ошибки подгрузки с повтором без потери уже показанных карточек.

## 7. Критерии приёмки и проверки

| Сценарий | Ожидаемый результат |
| --- | --- |
| Выпускник и преподаватель с подходящими данными | Оба находятся; роль не теряется у потребителей группового поиска. |
| Запись A: специальность X, институт I, 2020; запись B: Y, J, 2024 | X + J или X + 2024 не дают совпадения. X + I + 2020 дают человека и запись A. |
| Несколько совпавших записей | Один человек на странице; все показанные в карточке совпавшие записи удовлетворяют выбранным условиям. |
| Совпадение находится после первых 100 людей исходного каталога | Человек находится, поскольку фильтр применяется до ограничения страницы. |
| Более 200 людей, одинаковые имена и несколько Education | Страницы максимум по 100 уникальных пользователей; при неизменной БД полный проход без пропусков/повторов. |
| Нет фильтров, пустой q, человек без Education | Поведение соответствует явно принятому варианту из раздела 3; преподаватели не исчезают случайно. |
| NULL EndDate и отсутствующие FK | Без выбранного соответствующего фильтра карточка допустима; выбранный год/FK не совпадает с NULL. |
| Закрытый чужой профиль | В API и DOM нет лишних персональных данных; видны имя, образование и должность, просмотр disabled. Прямой GET `/users/{id}` остаётся 404. |
| Приватность изменена после загрузки | Сервер при прямом переходе повторно проверяет доступ. Собственный профиль сохраняет доступ владельца. |
| Чат: свой аккаунт, своя/чужая блокировка, недоступный аккаунт | Существующие ограничения и подтверждение собственной разблокировки сохранены, чужая блокировка не обходится. |
| Справочники изменились в БД | Новые значения доступны без редактирования HTML; одинаковые подписи не смешивают разные id. Годы не ограничены 2025 годом. |
| q с Unicode, пробелами, %, _, [, !; неверный limit/id/year/cursor | Корректный поиск литералов и предсказуемая валидация; SQL-инъекция и обход лимита невозможны. |
| Быстрые изменения фильтров и повторные клики подгрузки | Старый ответ не заменяет новую выдачу, страницы разных запросов не смешиваются. |
| HTTP и mock; создание/добавление участников группы | Совпадают правила поиска; legacy search.people остаётся массивом, UI групп и открытие чата работают. |

Порядок проверки при реализации: интеграционные SQL Server/API тесты семантики EXISTS, приватности и пагинации; контрактные тесты provider/normalization и совместимости групп; ручная проверка карточек и пагинации в браузере; измерение запросов и числа обращений к БД на представительном наборе данных. Использовать синтетические фикстуры, не менять реальные профили для проверки.

## 8. Последовательность поставки

1. Уточнить и записать принятие предложенных значений по умолчанию, сверить данные и окончательный DTO.
2. Реализовать серверный сервис поиска, справочники и новый API с интеграционными проверками; сохранить legacy-контракт.
3. Добавить клиентский контракт и mock, затем подключить страницу поиска и динамические фильтры.
4. Проверить приватность, чаты/группы, конкурентные запросы и производительность; обновить архитектурную документацию и индекс docs/README.md при поставке.

Готовность означает выполнение критериев приёмки, а не только заполнение карточек. Исходный документ сам по себе не разрешал реализацию или изменение БД; реализация выполнена по последующему запросу пользователя. Миграции и изменение реальных данных в эту поставку не входят.
