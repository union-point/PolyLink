# M1 identity and backed-up key setup

Implementation baseline: 18 October 2026. The approved admission flow is **operator-approved, single-use email/role invitations**, followed by ownership verification. Registry matching does not grant admission automatically. M1 keeps the [PLK1 formats](crypto-format.md) and [versioned API](contracts/openapi.yaml); messaging and account/history recovery remain M2/M4 work.

## Implemented paths

- Email-bound invitation enrollment, neutral registration responses, credential/browser-bound email codes and delayed activation. Existing legacy profiles are not changed before successful verification. Replacing pending credentials invalidates old verification and resend attempts. The invitation is consumed only at verified admission.
- Client Argon2id plus separate login/wrapping KDF contexts. Only the derived login secret reaches auth. Server hashing uses Spring Security Argon2id with a fresh 16-byte salt, 32-byte hash, parallelism 1, 64 MiB and three iterations; concurrent hashing is bounded to two operations. Original passwords remain in browser memory and never enter HTTP DTOs or storage.
- Optional email second factor as an inline login step. Verification codes last ten minutes, allow five wrong attempts and replace on resend after 60 seconds. Challenges are bound to an HttpOnly browser cookie, purpose, account and credential version. Reload discards unfinished password derivations and starts login again.
- Opaque, hashed access/refresh credentials with ten-minute access expiry, seven-day idle and thirty-day absolute refresh expiry. Every authenticated request checks current admission, verified email, credential version, expiry and revocation. Refresh rotation has a ten-second encrypted replay record for a lost/parallel identical refresh; its AES-GCM key is separate from SQL and from the code-MAC key. CSRF is a separate random session-bound cookie value with a server-side hash. All writes, including login/verification, require an allowed Origin.
- Client-created identity/vault, password copy and OpenBao service copy. Setup prepares an immutable package, checks the service round-trip outside SQL locks and atomically publishes a single winner. A failed or sealed OpenBao does not publish identity/vault state. The setup API never returns the open vault key. Completed setup drops redundant prepared ciphertext/verifier while retaining its idempotent result.
- Automatically created non-extractable AES-256-GCM device keys in IndexedDB, account/family/credential/vault-version binding, cross-tab notifications and automatic unlock after server validation. Access tokens live only in page memory; the obsolete localStorage token is removed. Storage failure permits password-based access and explains the missing navigation convenience. Logout clears local key capability and blocks reuse of a remaining cookie even if server revocation fails.
- Protected-page revalidation on focus, visible-page heartbeat and back/forward restoration. Back/forward cached contents stay hidden until session/key checks succeed. The owner-only profile endpoint supplies a minimal identity header; academic/profile editing and its remaining sections are outside M1.

The browser crypto assets are vendored from pinned libsodium.js 0.8.4. [The manifest](../../js/crypto/vendor/manifest.json) records source and vendored SHA-256 digests; the only wrapper change is its local ESM import. Regenerate with `npm ci --prefix tools/contracts && node tools/contracts/vendor-sodium.mjs` and review the diff. Password derivation runs in a dedicated worker, which terminates after returning its separated keys.

## Enable and provision

M1 is opt-in: `IDENTITY_ENABLED=false` by default. Follow the [guarded migration workflow](schema-and-migrations.md) and apply V3 in addition to V1/V2. V3 adds invitation/pending-enrollment state, challenge browser/credential binding and refresh replay state. It does not enroll legacy accounts, decrypt old chat or overwrite legacy hashes. M1 writes its verifier only in `auth.AccountSecurity`.

Configure the backend with separately supplied, persistent secrets and infrastructure:

| Setting | Value / purpose |
| --- | --- |
| `IDENTITY_ENABLED` | `true` after migrations and infrastructure are ready. |
| `FRONTEND_ORIGINS` | Exact comma-separated origins, e.g. `http://localhost:8001`; deployment uses HTTPS. Keep frontend/API host consistent so SameSite cookies work. |
| `AUTH_HMAC_KEY` | Independently generated 32-byte unpadded base64url secret for purpose-bound code/scope MACs and neutral salts; outside SQL/Git. |
| `AUTH_REPLAY_KEY` | A different 32-byte unpadded base64url AES key for ten-second refresh replay records; outside SQL/Git. |
| `OPENBAO_URL` | HTTPS address, e.g. `https://localhost:18200`; JVM trusts its CA. |
| `OPENBAO_TOKEN_FILE` | Protected file containing only the renewable narrow-policy service token. |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_AUTH`, `SMTP_STARTTLS`, `MAIL_FROM` | Real configured delivery; local capture defaults to localhost:1025. Production requires authenticated protected SMTP. |

All auth cookies use Secure, SameSite=Lax and Path=/ with `__Host-` names. Refresh and challenge credentials are HttpOnly; CSRF is intentionally readable. Local acceptance uses the localhost secure-context exception; ordinary deployment requires HTTPS. Browser requests never receive service tokens or administrative secrets. `OPENBAO_ALLOW_LOOPBACK_HTTP=true` exists only for explicit local adapter diagnostics; the committed infrastructure and full acceptance use TLS.

See the [OpenBao operator runbook](../../infra/openbao/README.md) for installation, manual unseal, narrow token provisioning, renewal, backup and failure behavior. Do not enable request-body logging/tracing for these endpoints. Secret DTOs and error responses are redacted; external proxy configuration must preserve that boundary.

From `backend/`, with the separate migration credentials already configured, approve an email and its role:

```sh
./mvnw compile exec:java -Dexec.mainClass=am.polylink.auth.AdmissionCommand -Dexec.args='invite approved@example.invalid graduate'
```

Use `lecturer` for an approved lecturer. The command creates a seven-day single-use authorization and revokes a previous unconsumed invitation for that email. It does not verify the mailbox or create a session. Registration's chosen role must match the approval. Existing admitted/deactivated/deleted accounts cannot be overwritten through registration. Administrative re-admission and automatic registry proof are not exposed through the public API.

For the application frontend, set `dataMode: 'http'` and the matching API origin in `js/config.js`; default mock mode continues to work independently. There is no silent HTTP-to-mock fallback. M1 supports auth and minimal owner identity reads; chat/other missing feature APIs still fail explicitly until their milestones are implemented. Lost-password routes remain unavailable until atomic recovery is implemented in M4.

## Limits and expiry

Aggregate limits supplement the per-code five-attempt cap. They use transactional SQL counters, MAC-protected scope IDs and the actual remote IP, not an arbitrary forwarded header.

| Operation | Account/scope limit | IP limit |
| --- | --- | --- |
| Pre-login parameters | — | 100/minute |
| Login secret verification | 10/15 minutes | 50/15 minutes |
| Code issuance / resend | 5/hour | 20/hour |
| Code verification | 10/30 minutes | 50/30 minutes |

A new challenge never bypasses these aggregate counters. Error responses carry safe codes and Retry-After where appropriate. SQL cleanup removes expired challenge/rate records, expires unfinished setup packages and drops expired replay material; durable send deduplication belongs to M2 and is not affected.

## Acceptance and remaining release checks

Run default backend checks with `./mvnw verify`. Full M1 acceptance requires Docker, a full JDK 25, an existing SQL Server instance with a disposable-database administrator, Node 22+, OpenSSL and the contract/browser dependencies:

```sh
npm ci --prefix tools/contracts --ignore-scripts
npm ci --prefix tools/m1 --ignore-scripts
npx --prefix tools/m1 playwright install chromium
python3 tools/m1/verify.py --browser
```

Set `DB_TEST_ADMIN_PASSWORD`, optional `DB_TEST_ADMIN_USERNAME`, and the SQL host/port first. Existing Linux/macOS SQL containers are reused without resetting their volumes. `M1_CHROMIUM` may select an already installed Chromium binary. The runner creates uniquely named disposable databases/containers, a temporary CA/truststore and test-only operator secrets, then cleans them up. It never migrates the working `polylink` database or sends email outside the local capture server. CI runs the same entry point; normal `./mvnw verify` needs no infrastructure.

Acceptance covers two admitted accounts, real SMTP delivery, inline factor/browser/purpose/attempt binding, neutral unauthorized enrollment, pending-credential replacement, key backup/publication, foreign-operation denial, sealed Transit, refresh replay/CSRF, revocation and local device storage. Browser phases cover registration/setup, reload/new tab, persistent browser restart with OpenBao sealed, failed network logout, and new-browser password/inline-factor access while OpenBao remains sealed.

Local acceptance passed on 18 October 2026:

- The working database remains at V2 with 60 users and 55 legacy messages; M1/V3 was not applied there. All disposable test databases and infrastructure containers were removed.
- 16 backend tests passed without skips: five default unit/HTTP tests and eleven SQL/infrastructure integration tests, including seven identity scenarios.
- Four fixed crypto tests and validation of the 34-operation OpenAPI plus positive/negative DTO/state fixtures passed.
- All three Linux Chromium phases passed: registration/setup/reload/new tab; persistent restart and offline logout with OpenBao sealed; new-browser inline email factor and password-copy unlock while Transit remains sealed. Captured browser API payloads contained neither the original password nor a raw-password field. Non-extractable AES-256-GCM `CryptoKey` persistence was verified.
- Chromium 156.0.8078.4 worker Argon2id at 64 MiB / two operations measured 392, 385 and 403 ms (median 392 ms). Server Argon2id at 64 MiB / three iterations measured 274/138/116 ms to encode and 121/124/122 ms to verify. These are single-machine observations, not latency guarantees.

Repeat the browser cost check with `node tools/m1/benchmark.mjs`. The standalone `tools/m1/ServerHashBenchmark.java` uses the dependency classpath generated at `backend/target/m1-classpath.txt` by the acceptance runner. Both use public synthetic fixtures and print only timings.

Actual macOS browser execution, hosted CI, production SMTP delivery, and production backup/restore rehearsal remain release checks on the target machines/environments; they cannot be inferred from a Linux headless run. M1 does not claim operator-inaccessible encryption or protection from a compromised host/browser.
