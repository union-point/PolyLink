# M3 session continuity and password lifecycle

Implemented 18 October 2026. M3 completes the shared protected-page/session coordinator and ordinary password change using the existing PLK1 password-copy format. It does not expose forgotten-password recovery, which remains M4, or implement unrelated settings/profile features.

## Deploy and use

Follow the [M1 setup](m1.md) and explicitly apply **V4** with the guarded [schema workflow](schema-and-migrations.md) before starting this backend version. V4 adds `auth.AccessTokens` and copies existing hashed access credentials with their expiry. It preserves existing users, sessions, vaults, messages and legacy data. Startup still never runs migrations. Auth/password APIs require `IDENTITY_ENABLED=true`; messaging additionally requires `MESSENGER_ENABLED=true` as described in [M2](m2.md).

Password change is available on **Settings → Password**. Enter the current and new passwords, then confirm the new password. The client checks the current password by opening the existing password copy locally, derives new separated login/wrapping secrets and verifies a new password copy of the same vault key. The authenticated, already-unlocked path also supports changing the password without submitting the old password to the API. Original passwords never enter HTTP DTOs or persistent storage.

The browser automatically signs in with the new derived login secret after activation. If email verification is enabled, it completes inline on Settings using the existing login challenge. Device storage is recreated before publishing the completed login or navigating. Leaving during verification discards derivations; ordinary login with the new password completes access. Changing a password does not invoke OpenBao.

Unimplemented settings controls remain disabled in HTTP mode; they cannot prevent the password editor or local theme controls from loading. Email change, account lifecycle, general preferences and academic profile editing retain their existing milestone scope.

## Password transactions and retries

`POST /auth/password-change/prepare` accepts the M0 `PASSWORD_CHANGE` package and returns `OperationStatus`. It validates all expected independent versions, the unchanged vault and public identity, a new salt, parameter bounds and canonical password-copy sizes. A session alone cannot replace the encrypted vault, identity or service copy through this route. Slow server verifier hashing happens before SQL locks; the service rechecks the session and every base version after taking the account lock.

Preparation stores only the new salted server verifier and encrypted password copy/derivation metadata, bound to the initiating session family. Packages are immutable and expire after fifteen minutes. Matching retries reuse the package; changed bytes conflict. No plaintext login secret or vault key is persisted. Ordinary session authorization remains required; there is no service-unlock capability.

`POST /auth/password-change/commit` locks the account and checks its current session, package authorization, expiry and base versions. One transaction replaces the verifier/KDF metadata/password copy, increments credential version, revokes all old sessions and pending email challenges, cancels competing unfinished key operations and records an immutable completion result. Vault bytes, vault-key version/content revision, identity and service copy remain unchanged. Competing changes have one winner.

For a lost commit response, the original unexpired access token can retrieve **only its own completed operation result**, bound to that operation's initiating family and original expiry. It cannot prepare, activate another operation, refresh a revoked session, read a vault or authorize any other API. A current authenticated owner may also retrieve a completed result. The transport deliberately keeps the original bearer for this bounded replay rather than replacing it through refresh. The client repeats an ambiguous commit before attempting automatic login; it never resubmits a newly encrypted password package as a substitute for an unknown activation.

## Pages, tabs and storage

- Access tokens remain in page memory. Refresh cookies retain seven-day idle/thirty-day absolute expiry. V4 gives each refresh a separately hashed access credential with its own ten-minute expiry, so refreshing one tab no longer invalidates another tab's still-valid token. Session/credential revocation is still checked on every authenticated request; expired access records are cleaned up.
- Refresh requests coalesce per page and coordinate through Web Locks when available. Transport generations reject late responses after a session change/logout. Refresh failures are sanitized and cannot retain Axios configs containing sensitive fields. Retried encrypted requests preserve the original operation and bytes.
- All protected pages use the shared coordinator. Session, family and all vault/credential/identity versions are checked before opening a device copy. Concurrent restores share one request chain. Broadcasts carry events/versions, never open secrets or access credentials. Stale device cleanup checks its original family/credential binding before deleting a replacement device record.
- Login → profile → chat, reload, another tab and persistent browser restart open the validated device copy without running Argon2id or Transit. A clean browser uses the password copy and retained room envelopes to open history with OpenBao sealed; it does not publish a new identity.
- Back/forward restoration hides sensitive page content until server/key validation completes. Temporary network failure does not open a device key or silently become an offline unlock. Revocation causes local key cleanup and protected-page exit. Session changes reload protected views so decrypted state from an older account/version is discarded.
- IndexedDB/CryptoKey persistence failure produces an explicit notice and permits password-based reading on the current page. Navigation requires normal password login again. History reads tolerate unavailable outbox storage, while new sends continue to require durable encrypted storage before POST. No open-key localStorage fallback exists.
- Logout clears local memory/device/outbox capabilities even if the server request fails. A persistent local marker blocks reuse of the remaining refresh cookie until explicit login; a readable Secure cookie supplements the localStorage marker when localStorage is unavailable. Page contents are concealed immediately, and other tabs receive logout events. The UI reports an unconfirmed remote revocation separately from successful local logout.

## Verification

Use a full JDK 25, Node 22+, Docker, OpenSSL and the disposable SQL administrator credentials from the M1 instructions:

```sh
npm ci --prefix tools/contracts --ignore-scripts
npm ci --prefix tools/m1 --ignore-scripts
npx --prefix tools/m1 playwright install chromium
npm test --prefix tools/contracts
./backend/mvnw -f backend/pom.xml verify
python3 tools/m1/verify.py --continuity
```

`--continuity` includes all SQL/HTTP/migration checks and M1/M2 browser scenarios, then runs M3 with OpenBao sealed. The runner uses uniquely named disposable databases/containers and temporary test secrets; it does not migrate the working database. Missing required infrastructure fails the run. CI invokes this same command.

The SQL tests cover immutable package preparation, owner/family denial, concurrent changes, expiry, verifier/copy activation, unchanged vault/identity/service data, old-password rejection, revocation of other sessions, completed-only replay and independently valid access credentials with idle/absolute expiry. Focused client tests cover parallel refresh coalescing, late refresh after logout, exact encrypted request retries, sanitized errors, status-only password commit replay and blocked-storage reads/send prevention.

The Chromium phases cover cross-page and cross-tab unlock, cached-page restoration gating, network failure before any device open, clean-browser history, blocked IndexedDB, persistent process restart, a deliberately lost successful commit response, optional inline email verification, history after password change, new device records across tabs, old-password/other-session denial and local logout while the server is unreachable. Captured payloads must contain neither original password nor a setup/service key submission.

Local acceptance on 18 October 2026 passed without skips: 21 backend tests (five default and sixteen SQL/infrastructure integration checks), eleven crypto/client tests, OpenAPI/DTO/state validation, all M1/M2 browser checks and the three M3 Chromium phases. Temporary test databases and containers were removed; no working database was migrated.

Actual macOS browser execution and the later recovery/restore release rehearsals remain required; a Linux Chromium run does not establish those results.
