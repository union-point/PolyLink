# M6 dynamic groups and account lifecycle

Implemented 19 October 2026. Apply V7 explicitly after V6; startup never migrates a working database. M1–M5 packets, epochs, recovery and personal state remain compatible.

Groups contain 2–100 distinct configured, admitted, verified accounts at creation and may retain one member afterwards. Names are trimmed, 1–100 UTF-16 units. Only the owner renames, transfers ownership, adds or removes members. Members may leave; the owner first transfers ownership unless alone. Direct blocks have no group effect. Group mutation requests have a 60/hour/account budget; preparation is bounded to 120/hour/account. UUID operation IDs are durable per account, with a fingerprint of the complete immutable request; matching retries return a minimal recorded result and differing requests conflict. Metadata revisions are independent of membership revisions.

Creation prepares a client-selected room UUID and the complete recipient snapshot. Addition prepares the complete future snapshot with membership revision incremented once. Both commit a fresh PLK1 epoch and complete envelopes atomically with membership. No identity or missing-backup error changes membership. Removal/leave revoke membership immediately, advancing membership revision; current clients resume ordinary automatic epoch activation. No send can use the former epoch. Rename/owner transfer do not rotate keys.

Current membership intervals gate history, files, previews, unread, export and saved-send results. Rejoining sets JoinedSequence to the committed LastSequence + 1, resets personal history/read state, and starts a new membership revision. Envelope access also checks JoinedMembership, preventing access to an earlier epoch when departure/rejoin occurred without messages. Historical intervals and author references remain for integrity.

V7 assigns existing encrypted groups to the lowest admitted, verified participant ID and preserves their intervals, ciphertext, envelopes and personal state. Groups without an eligible owner close. Legacy dbo chat data stays in its original tables, clearly separate from encrypted history; original timestamp timezone remains unknown and no UTC conversion is invented. Import of legacy group membership requires an explicit reviewed mapping and admitted, configured accounts; plaintext bodies are never imported as encrypted messages.

Approved lifecycle policy: deactivation suspends admission/sessions without changing group membership or ownership. Account deletion removes own message/image bodies and vault copies, retains neutral sequence positions and operation tombstones, revokes membership immediately, closes direct rooms, and assigns owned groups to the lowest remaining eligible account ID or closes them. A deletion ledger must be retained outside restored backups and replayed before serving a restored installation. M7 must rehearse this process and agree production backup retention. Local copies already obtained by participants cannot be erased remotely.

## Deployment and operations

Use the existing M1 identity/messenger opt-ins, TLS, origin and SMTP/Transit configuration. From `backend/`, apply migrations with separate migration credentials using the guarded `SchemaCommand upgrade`. V7 is additive; take the normal SQL safety backup first. Never run an older messenger binary after dynamic membership has been enabled: older binaries do not enforce the new intervals. Roll forward with a compatible binary; a database rollback also requires the separately retained deletion ledger before access is restored.

For an explicitly reviewed legacy group, retain the existing account IDs and select its owner. All mapped participants must already be admitted, verified and fully configured. The operator command imports only the legacy membership, gives it a new encrypted-room UUID and preserves a unique mapping to the legacy room ID. It never converts or copies plaintext messages or guesses their timezone. Exact retries return the existing room; its first unlocked member prepares the initial epoch automatically.

```sh
./mvnw -q compile exec:java \
  -Dexec.mainClass=am.polylink.chat.MessengerMaintenanceCommand \
  -Dexec.args="import-group 12 34 'Reviewed group name'"
```

Here `12` is the reviewed legacy room ID and `34` is an existing participant's admitted account ID. The command uses `DB_NAME`, `DB_HOST`, `DB_PORT`, `MIGRATION_DB_USERNAME`, `MIGRATION_DB_PASSWORD` and `DB_TRUST_SERVER_CERTIFICATE`, exactly like the schema command. It does not read local config files. Missing identities reject the entire import. Existing encrypted groups are initialized by V7 itself.

Deletion is a soft account tombstone to preserve non-cascading author and key references. New messenger bodies owned by the account and private attachment bytes disappear in the same transaction as membership revocation, owner succession and session revocation. Historical public identities, interval boundaries, sequence positions and minimal deduplication receipts remain; they cannot authorize access. Own legacy plaintext bodies are replaced with a neutral marker only on explicit account deletion. The current vault/password/Transit copies and prepared recovery packages are removed. Other participants' bodies remain. Closed direct rooms retain the peer's allowed historical view and reject new sends.

Deactivation keeps the current intervals, ownership and password copy. Existing sessions are revoked, pending challenges/recovery are cancelled, and admission suspends reads/sends/recovery. It does not invalidate the password-copy binding. As in M5, a retained deactivated participant prevents new sending/key activation until the owner removes that participant or an operator re-admits the account. An ordinary login cannot reactivate it. Attempts involving an unavailable peer return a permission error and preserve the active caller’s session.

Retain the cumulative deletion ledger **outside SQL backups**, with restricted operator access. Export it after deletion processing and before backups are retired; preserve the union across exports. Backup restores must remain offline until migrations and ledger replay succeed. The ledger contains account IDs, not authentication or encryption keys.

```sh
./mvnw -q compile exec:java \
  -Dexec.mainClass=am.polylink.chat.MessengerMaintenanceCommand \
  -Dexec.args=export-deletions > /secure/operator/deletion-ledger.json

# Against the restored database, while application access is disabled:
./mvnw -q compile exec:java \
  -Dexec.mainClass=am.polylink.chat.MessengerMaintenanceCommand \
  -Dexec.args='replay-deletions /secure/operator/deletion-ledger.json'
```

Replay is idempotent, skips accounts absent from older backups, and tombstones legacy accounts whose backup predates security enrollment. It applies the same group departure/body deletion transaction as account deletion. Do not overwrite a newer external ledger with a restored database's older ledger. Production backup schedules, retention periods, coordinated SQL/OpenBao restore, retained Transit versions and replay rehearsal remain M7 release work.

## Browser and API behavior

**Messages → Create group** selects admitted people by name. **Group members** exposes rename/add/remove/transfer to the owner and leave to members. The server supplies management permissions, expected membership/metadata revisions and public identity snapshots. Missing setup explains the rejected recipient while the group keeps its previous membership and epoch. Personal direct blocks do not change group rights. One-member groups remain usable; the last departure closes them.

The client creates an independent random key for each membership epoch using the existing PLK1 sealed-envelope format. It prepares crypto before mutation, stores the complete group request encrypted under the vault key before HTTP, retries identical bytes after ambiguous outcomes/reload, and rebuilds only after a definitive revision rejection. Minimal group receipts disclose no history or keys, including a member's own completed leave. Message replay remains governed by the current interval. Inaccessible old send retries are discarded without automatically resending into the new interval.

Text composer drafts are stored encrypted in IndexedDB. Polling/membership changes preserve text, selected images and scroll position. Reload restores text; browsers require selecting an unsent file again. If secure storage is unavailable, reads remain available and new mutations fail before their first HTTP commit. Automatic key rotation resumes from room snapshots after reload or another participant's next session. No manual key action, peer confirmation or password prompt is introduced for groups.

Membership changes and direct closure reconcile loaded message positions, including deletion markers, while preserving the viewport. Already delivered local content cannot be revoked remotely. Own export paginates accessible caller-authored ciphertext on the server and decrypts text and image bytes in the browser; it includes no participant bodies, room envelopes, vault packets or private keys. Export is a sequence of authorized page reads, not a database-wide snapshot during concurrent changes.
