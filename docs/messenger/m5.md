# M5 messenger UI, images and personal state

Implemented 18 October 2026. Explicitly apply **V6** through the guarded [schema workflow](schema-and-migrations.md) before starting this version. Startup never migrates the working database. Existing identity/messenger opt-ins and [M1 deployment prerequisites](m1.md) remain in effect.

## Private encrypted images

Private object storage is **SQL Server**, in `messaging.AttachmentBodies`. V6 adds a bounded ciphertext body keyed by the existing attachment UUID; no public filesystem/static URL or separate storage credential is introduced. SQL backups include ciphertext objects with their metadata. A future external-object adapter would need its own reviewed lifecycle/backup contract.

The browser accepts one PNG, JPEG, GIF or WebP of 1 byte through **5 MiB**, with empty text permitted for an image-only message. Both sender and receiver check actual signatures, declared type/size and browser image decoding. Text is trimmed and bounded to **5,000 UTF-16 code units**; receivers reject authenticated payloads violating the same rules. The server sees opaque ciphertext and its size, not an asserted inspection of plaintext type or text length.

Each image has a new random key, 24-byte nonce and client UUID. XChaCha20-Poly1305 binds its ciphertext to `PLK1/image/room/owner/attachment`. The image key, nonce, original filename, type and size live inside the encrypted message metadata. Upload HTTP bodies contain only binary ciphertext; filename, MIME type and open image keys never enter upload headers/SQL metadata. Ciphertext is plaintext length plus 16 bytes, with a **5,242,896-byte** HTTP/storage cap. General identity JSON requests retain their smaller limit.

`POST /chat/rooms/{roomId}/attachments` accepts `application/octet-stream` and `X-Attachment-Id`. The owner, room, digest and bytes are immutable. Exact retries return the same object; changed bytes conflict and foreign objects are unavailable. Staged objects expire after 24 hours without extending on retry. Uploads have a 60-attempt/hour account budget and at most 20 unexpired staged objects / 100 MiB of staged plaintext-equivalent capacity, plus AEAD overhead. Retries consume that request budget.

Message submission validates upload ownership, room, expiry and unbound state, then inserts the message, binds the object, records the dedup result and advances the room sequence in one transaction. A failure after binding rolls all of them back. A matching saved-message replay resolves before new key/permission checks; a bound object cannot be attached to another operation.

The scheduled cleanup removes up to 100 expired unbound bodies per minute. It retains small ID/digest/expiry tombstones so delayed upload retries cannot recreate a UUID with different bytes. Bound objects are retained for message history, regardless of their original staging deadline. Body removal and tombstone retention are deliberate; account/content deletion remains M6.

`GET /chat/attachments/{attachmentId}` requires a Bearer credential and current membership/history-cutoff/deletion authorization. Unbound objects cannot be downloaded, including by their uploader. A hidden participant loses server download access to old objects; another authorized participant keeps access. The client authenticates/decrypts and decodes the image before creating a blob URL. URLs are cached only in memory and revoked on disposal, room changes, hiding, identity/session changes and page exit. Room previews decrypt metadata locally without downloading images. Binary error responses retain safe API error codes.

## Durable image retries

The vault-encrypted IndexedDB outbox now holds prepared image-upload ciphertext as well as the immutable message request. Its decoder has an explicit 12 MiB limit sufficient for a maximum image and base64/packet overhead; vault/message format limits are unchanged. No open draft/image key or filename is stored outside the encrypted packet.

The full candidate is durably saved **before upload**. A lost upload reply retries identical UUID/bytes. A lost send reply retries the same message operation/packet, including after reload and key rotation. Only a definitive unsaved key rejection permits a new message operation; the client performs bounded fresh-snapshot retries and can reuse the same staged image. After a reload, retrying a definitively rejected image requires selecting the image again; an empty composer cannot silently revive that attachment. Unknown outcomes still retry their original stored bytes. Once a result is known, large upload bytes and open attachment metadata are removed from the persisted result record. Blocked storage prevents a new send before its first HTTP upload.

## Personal conversation state

- `PUT /read` takes `throughSequence`, an accessible displayed sequence. It advances monotonically under the room lock, rejects future/inaccessible positions and never substitutes the server's latest sequence.
- `PUT /mute` takes `enabled` and updates only the caller's preference. It does not clear unread state.
- `POST /hide` takes an empty object. It records the current committed sequence as the caller's cutoff and hides that participant's view. Old message bodies/downloads remain inaccessible through that view. An incoming message reveals the room without removing its cutoff; opening a direct room also retains the cutoff.
- `PUT /chat/blocks/{userId}` changes only the caller's block. Direct send/upload/key activation checks both directions. Retained history remains readable, and direct blocks do not affect group sends. `Room.blocked` describes the caller's own block; `canSend` is the authoritative send control without exposing a peer's block flag.

All these operations share the existing account-before-room lock order with sends and key activation. Room-list cursors keep their fixed ID ordering but rehydrate each returned room against current authorization, hide state and cutoff. An earlier scan cannot return an old preview after hiding. If another tab hides a room and incoming activity reopens it before the next poll, the increased cutoff resets the cached view rather than retaining old loaded records.

## History and polling UI

The UI uses `chat.page`, defaulting to the latest 50 messages. Older pages use exclusive `before` cursors; catch-up uses exclusive `after` cursors in ascending pages, advancing only after successful decryption/merge. The existing `chat.messages` convenience method still returns complete decrypted history for compatibility; the UI no longer uses it for every poll. IDs deduplicate records and SQL BIGINT sequences stay decimal strings/BigInts.

Prepending and incoming merges preserve a visible message anchor. Unchanged polls do not rebuild message DOM. Images reserve a stable display box. Incoming messages do not move a reader who is above the bottom; a new-message button provides an explicit jump. Search is labeled **Search loaded history only** and filters the loaded plaintext locally.

Read acknowledgement is debounced and gated on a visible document and actual rendered viewport positions, including completed image rendering. A message larger than the viewport is acknowledged when its bottom is displayed. Off-screen arrivals are not acknowledged merely because a history response or room summary contains them.

Polling has one request chain per selection, cancellation/generation guards, an approximately 2.5-second visible-page interval, jitter and bounded exponential backoff. Reconnect/refocus/visibility restoration reconcile immediately. Polling failure retains loaded history, scroll position, compose text and selected files. Requests from a previous selection cannot replace the current view or create a late plaintext image URL. Personal actions and composition use the same multipage service boundary.

The mock provider upgrades its local chat fixtures once from timestamp markers to decimal sequences, then uses the same pagination, read/cutoff, incoming-reopen, mute and direct-only block rules. Its images remain explicit local demo data; it does not claim production encryption.

## Verification

```sh
npm ci --prefix tools/contracts --ignore-scripts
npm test --prefix tools/contracts
python3 -m pip install -r tools/contracts/requirements.txt
python3 tools/contracts/validate.py
./backend/mvnw -f backend/pom.xml verify
npm ci --prefix tools/m1 --ignore-scripts
npx --prefix tools/m1 playwright install chromium
python3 tools/m1/verify.py --messenger-ui
```

The full runner includes M1–M4, then fresh M5 browser fixtures and both HTTP/mock UI scenarios. It requires JDK 25, SQL administrator variables and Docker as documented in M1. It uses disposable databases, real TLS OpenBao with the restricted service policy, SMTP capture and isolated browser profiles; missing dependencies fail. CI and the local full-check command use this runner. For focused M5 iteration, `--messenger-ui-only` runs its SQL/HTTP and both browser scenarios without claiming M1–M4 regression coverage.

SQL/HTTP checks include the maximum ciphertext body, immutable retry/owner checks, unbound/foreign/private download denial, atomic binding rollback, expired-body cleanup/tombstones, bound-object retention, hidden download/history denial, incoming reopen, monotonic/future read checks, personal mute, bilateral direct denial, unaffected group send and stale room-scan filtering. Client checks cover maximum-image encrypted outbox reloads, exact upload/send bytes, image tamper/type/size rejection, authenticated invalid text, BIGINT merges, viewport acknowledgement and sequence-based mock behavior.

The Chromium scenarios cover bounded initial history, prepending anchors, off-screen unread arrivals, loaded-history search, polling failure/reconnect with draft retention, all four image formats, exact 5 MiB input, image-only sending, lost upload and send responses across reloads, private downloads, mute, direct blocks, fixed groups and hide/reopen. Supported macOS browsers and production retention/deletion/restore rehearsals retain their M6/M7 scope.

Acceptance on 18 October 2026 passed without skips: **31 backend tests** (six default and twenty-five SQL/infrastructure checks), **23 client crypto/session/state tests**, OpenAPI/DTO/state validation, twelve local-tool checks and the complete M1–M5 Chromium run. The M5 HTTP and mock scenarios passed both in focused isolation and in the full regression run. Decorative third-party fonts/backgrounds are isolated by the browser harness; application JavaScript, crypto, SQL, OpenBao, SMTP and private image requests execute normally. Disposable databases/containers/profiles were removed; the working database was not migrated.
