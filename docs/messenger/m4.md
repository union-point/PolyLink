# M4 atomic recovery and room-key rotation

Implemented 18 October 2026. Apply **V5** using the guarded [schema workflow](schema-and-migrations.md) before running this version. Startup still never migrates databases. Existing `IDENTITY_ENABLED` and `MESSENGER_ENABLED` opt-ins remain in effect. Follow [M1](m1.md) for mail/OpenBao configuration and [M3](m3.md) for ordinary session/password behavior.

Use **Forgot password → email code → new password**. The browser automatically signs in after activation and recreates its encrypted device copy before navigation. A reload of the reset page resumes from its recovery cookie. Recovery never changes admission, email ownership or account lifecycle state.

## Authorization and transactions

Recovery requests use neutral unknown-account responses and the existing account/IP limits, with additional preparation and automatic-login budgets. Codes are six digits, expire in ten minutes, permit five incorrect attempts and have a sixty-second resend delay. V5 binds challenges to the email address at issuance. Merely requesting/resending a code leaves sessions and verified recovery untouched. Successful verification creates a new operation and cancels prior unfinished recovery for that account.

A separate `__Host-plk-recovery` Secure/HttpOnly/SameSite=Lax cookie authorizes one operation for thirty minutes. Its original expiry never slides. Only its hash and the independent recovery-CSRF hash enter SQL. Mutation requests need the readable `__Host-plk-recovery-csrf` cookie and matching `X-CSRF-Token`, plus the allowed Origin enforced by the shared boundary. Access/refresh tokens alone cannot authorize recovery or service unlock. Account selection, base versions and service ciphertext always come from the operation, never from caller-supplied account IDs or Transit ciphertext.

`request`, `verify`, `status`, `unlock`, `prepare`, `commit` and `login` live under `/auth/recovery`. The [OpenAPI contract](contracts/openapi.yaml) defines their DTOs. Status includes public account identification and whether an immutable package has been selected, so reloads do not depend on a stored email code or an exposed recovery token.

Service unlock durably selects `RECOVERY_SERVICE` and `WAITING_SERVICE` before invoking Transit. The server decrypts only its stored owner/version/context-bound service copy, then revalidates authorization and all base versions before returning the transient key. A completed, superseded, expired or changed-account operation cannot unlock. The browser opens the vault, retains all historical identities, creates a new identity and random vault key, increments vault key/content versions, and validates both its new encrypted vault and password copy.

`RECOVERY_LOCAL` requires the verified recovery cookie plus a current authenticated owner session. The browser uses its already-open current key; the server verifies the unchanged vault/identity and preserves the service copy, identity and vault versions. This path does not call Transit.

Preparation selects an immutable fingerprint before slow work. Only encrypted packets, public metadata, a salted server verifier and Transit ciphertext are persisted. Hashing and Transit round-trip validation happen outside SQL locks; account authorization, email, admission and all independent base versions are checked again afterward. An unavailable Transit leaves the existing credentials/copies active and permits retrying the same candidate. No raw login secret or vault key is persisted by the backend.

One account-locked transaction replaces credentials/KDF metadata/password copy and, for service recovery, the vault/service copy and identity. It revokes all prior sessions and unused email challenges, cancels competing operations and records a completed result. Old identities/envelopes are retained for historical decryption. Commit/status repeats return that same result after a lost response. Completed cookies cannot prepare or unlock; they retain status/commit-result access until original expiry.

`login` consumes a single purpose-bound email-verification handoff together with session creation, checking the new derived secret and completion versions. This satisfies optional email verification for the next automatic login. A lost login response can require ordinary login/optional verification; it cannot mint repeated sessions through the handoff.

## Browser resumption and rotation

The reset page never stores the new password, email code or an exposed recovery credential. Before preparation, it saves an encrypted candidate in sessionStorage, protected by the new password-wrapping key and bound to account/operation. The record contains only public KDF metadata and an AEAD packet. Re-entering the same new password resumes the exact candidate bytes after reload or failure. If browser storage is blocked, preparation stops with an explicit storage error. Losing that encrypted candidate before readiness requires a fresh recovery verification; a ready/completed operation can still commit/sign in through cookie/status and password re-entry.

An already-ready operation commits without another service unlock or vault re-encryption. A completed operation signs in using the current password parameters. Ambiguous prepare responses consult status, and ambiguous commits retry the same operation. All derived keys and temporary plaintext key arrays are cleared on exit.

Reading active history starts rotation for the open room without delaying historical decryption. Room-summary reconciliation queues other sendable stale rooms. Protected-page session restoration also queues a scan once per validated session/version, so navigation after recovery resumes work. Each activation uses the complete current membership/recipient identity snapshot and sealed envelopes, with bounded retries when another participant wins. Later clients/polls resume unfinished work. A configured participant can rotate with all peers offline. Missing published keys continue to block sending. Existing send deduplication resolves matching historical operations before checking key freshness.

## Verification

```sh
npm ci --prefix tools/contracts --ignore-scripts
npm test --prefix tools/contracts
python3 -m pip install -r tools/contracts/requirements.txt
python3 tools/contracts/validate.py
./backend/mvnw -f backend/pom.xml verify
npm ci --prefix tools/m1 --ignore-scripts
npx --prefix tools/m1 playwright install chromium
python3 tools/m1/verify.py --recovery
```

Use a full JDK 25 and the isolated SQL administrator variables documented in [M1](m1.md). The acceptance runner creates disposable SQL databases, a real TLS OpenBao server with the restricted backend policy, and captured SMTP delivery. Missing dependencies fail the run. CI and the local full-check script run `--recovery`, which includes M1–M3 checks.

Recovery SQL/HTTP tests cover missing/foreign capabilities, CSRF, arbitrary unlock fields, immutable packages, concurrent commits, supersession, expiry, changed email, service failures before unlock/readiness, completed-only key denial, historical identity retention, local-copy preservation, injected mid-activation SQL rollback, revocation and one-use login handoff. Client crypto tests cover historical private-key preservation, new identity/key generation, exact encrypted candidate resumption after failure, wrong-password denial and lost prepare/commit responses. Chromium scenarios exercise the actual reset UI and cookie/status reload, local recovery while Transit is sealed, service recovery from a clean browser, retained direct/group histories with peers offline, automatic epoch activation and post-recovery sends. A second direct-chat participant then recovers independently, including the email-factor handoff.

Linux Chromium evidence does not replace the macOS/supported-browser and disaster-restore rehearsals scheduled for M7. Images, personal state, account lifecycle and production group initialization retain their later milestone scope; fixed group fixtures here establish recovery behavior.

Acceptance on 18 October 2026 passed without skips: 26 backend tests (five default and twenty-one SQL/infrastructure checks), fifteen client crypto/session tests, OpenAPI/DTO/state validation, eleven local-tool checks, all M1–M3 browser phases and the three M4 Chromium phases. The service phase interrupts after readiness, reloads from the cookie/status and repeats a deliberately lost successful commit response. Disposable databases and containers were removed; the working database was not migrated.
