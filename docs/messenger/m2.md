# M2 encrypted direct text slice

Implemented 18 October 2026 against the existing PLK1 contracts and V2/V3 storage. M2 adds no migration and never imports or modifies plaintext legacy conversations. Account/history recovery, images, personal-state mutations, existing groups and the full history UI remain assigned to M3–M6 in the implementation plan.

## Enable and use

Complete the [M1 deployment prerequisites](m1.md), explicit migrations and invitation enrollment first. Set `MESSENGER_ENABLED=true` alongside `IDENTITY_ENABLED=true` when starting the backend. Messaging is disabled by default; its controllers and allowed security paths require both flags. The frontend's existing HTTP provider now uses the encrypted chat client.

Two invited, email-verified users must each finish a password login and backed-up key setup. Open the existing Search page, find the other user, and choose **Connect** to open the unique direct room. The recipient may then be offline: the sender activates envelopes for both configured identities, and the recipient opens its envelope on its next authenticated visit. An unconfigured recipient prevents sending with an explicit pending-key error.

The existing `/search?q=` mapping now has a minimal authenticated, admitted-account directory supporting Connect. It returns at most 100 matches, ordered by name and user ID, with public ID/name/role and onboarding state; it exposes no email or key secrets. Search metacharacters are escaped. General profile browsing and richer directory filters remain outside this slice.

## Server behavior

The implemented contract paths are `POST /chat/direct`, `GET /chat/rooms`, `GET/POST /chat/rooms/{roomId}/messages`, `GET /chat/rooms/{roomId}/keys` and `POST /chat/rooms/{roomId}/keys/activate`. Protected controllers use the M1 session verifier, no-store/origin boundary and non-enumerating chat 404 responses.

- Account-security rows lock in ascending ID order before the room row. Direct creation holds both account locks, so reversed/concurrent opens share the canonical unique pair. Key activation accepts one complete current recipient snapshot. Missing keys never enable plaintext sends.
- New sends recheck membership, account admission, direct blocks, closure, identity snapshots and the accepted key epoch. The room counter, message and durable send operation commit together. The room lock remains held through commit; a later sequence cannot become a visible cursor ahead of an earlier uncommitted message. SQL deadlock victims retry the whole transaction at most twice.
- An accessible matching operation resolves before key freshness checks; altered bytes conflict. Cutoff/membership restrictions apply to replay results and history. Tombstone/dedup records are not expired by M1 cleanup.
- History uses exclusive decimal-string sequence cursors, default 50 and maximum 100. `after` pages ascend, `before` pages return ascending records from the requested older slice. The browser compares counters with `BigInt` and drains catch-up pages before finishing a refresh.
- Room-list scans retain immutable, account-bound summaries for 30 seconds, sorted by activity then room ID. Opaque cursors traverse bounded pages; expired/evicted scans conflict. The process retains at most 256 scans, rechecks access on each page and loses scans safely on restart. The browser publishes a replacement list only after completing its scan.
- Envelopes are returned only to their recipient, for current or currently accessible historical epochs. The server stores only ciphertext and metadata; neither message operations nor history access call Transit or Argon2id.

## Browser behavior

`js/chat/encrypted-client.js` owns crypto orchestration; `js/data/http/routes.js` owns wire mappings. Controllers receive decrypted render models. Each received sealed box is checked against its room, recipient, historical identity, membership and key version. Message AEAD binds the sender and operation before sequence allocation. Trimmed text must contain 1–5,000 UTF-16 units and decrypt to the agreed text-only payload.

Before sending, the client encrypts the complete immutable operation and draft text under the unlocked vault key and saves it in `polylink-outbox-v1` IndexedDB. Storage failure prevents the HTTP send. The record's AAD binds account, room, operation and vault-key version. Ambiguous failures retain the same operation, nonce and ciphertext. Reloading/selecting the room retries that original request before preparing new messages, including after room-key changes. A durable encrypted completion receipt prevents a retried composer draft from becoming a second message after background reconciliation; submitting that draft acknowledges the receipt. A different draft is retained with a prompt to send again after resolving the previous operation. Definitive unsaved validation/permission/key rejections permit a later fresh operation. Payload conflicts stay unresolved for explicit investigation.

Logout/session revocation clears account outbox records alongside M1 device records and secrets. The browser never persists plaintext drafts or open room keys. Polling runs approximately every 2.5 seconds while visible, reconciles on refocus/reconnect and avoids overlapping refresh chains. Failed refreshes retain the existing compose/history state. This basic slice drains history from sequence zero; bounded loaded-history pagination, scroll anchoring, backoff and real read/unread/hide/mute/block UI belong to M5. M2's read callback deliberately makes no server acknowledgement, and unimplemented personal-state/image mutations fail explicitly.

## Verification

From the repository root, with a full JDK 25, Node 22+, Docker, OpenSSL and disposable SQL administrator credentials configured as for M1:

```sh
npm ci --prefix tools/contracts --ignore-scripts
npm ci --prefix tools/m1 --ignore-scripts
npx --prefix tools/m1 playwright install chromium
npm test --prefix tools/contracts
./backend/mvnw -f backend/pom.xml verify
python3 tools/m1/verify.py --messenger
```

`--messenger` runs the full SQL/HTTP/migration profile, M2 Chromium scenarios and the three existing M1 browser phases. Missing dependencies fail rather than skip. The runner resets rate-limit counters only in its uniquely named disposable database between the independent HTTP and browser suites, so their shared loopback IP does not consume a production-sized aggregate budget. CI invokes this same entry point.

`ChatIT` exercises parallel direct creation, parallel competing key activation, concurrent duplicate sends, mismatched fingerprints, outsider denial, offline-recipient history/envelopes, identity-change replay, bounds and explicitly delayed commit ordering using separate connections. The production browser client also has focused tests for envelope binding, storage failure before POST, exact encrypted retries and message sender/AAD tampering. The Chromium scenario uses three isolated contexts, actual IndexedDB and the vendored libsodium asset; it drops a successful send response, reloads, reconciles the outbox, verifies one message, starts a conversation through Search/Connect and observes a polled decrypted arrival. Captured chat request bodies must contain none of its plaintext canaries.

Local acceptance on 18 October 2026 passed with no skipped tests: 18 backend tests (five default checks and thirteen SQL/infrastructure integration checks), seven crypto/client tests, the M2 Chromium scenario, and all three M1 browser phases. The isolated SQL databases and temporary TLS OpenBao/SMTP containers were removed after the run; no working database was migrated.

Linux Chromium evidence does not replace macOS/supported-browser acceptance or the later recovery/operational release rehearsals.
