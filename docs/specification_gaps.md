# PolyLink specification gaps

Reviewed 15 October 2026. This lists behavior that is still undecided in `frontend_context.md` and `backend_design_context.md`. Each item is something an implementer would otherwise have to invent.

The documents already name most of these gaps. What is missing is one answer per item, specific enough to implement without copying the mock. Mock rules are demo behavior, not production policy, unless a decision below explicitly adopts them.

Settled facts that this list does not reopen: member pages require a session and completed onboarding; announcements are posts, not a calendar; forum replies are flat; ids at the API boundary are opaque strings; timestamps are ISO UTC; the server, not the client, is the authority for ownership, membership, and visibility.

## Eligibility and roles

- **Who may register.** The database report allows only `@polytechnic.am`. The client accepts any syntactically valid address, and fixtures use other domains. Decide the exact allowlist, including letter case, plus-tags, and subdomains, and whether alumni who no longer have a university mailbox are an exception.
- **How a graduate is matched.** `AlumniRegistry` has no email. Its unique key is `DiplomaNumber`, and no screen collects a diploma number. Matching on name alone is not proof. Decide the evidence (diploma number, a registry email, or another field), what the user sees when zero rows match and when several match, and whether one diploma can be claimed by only one account.
- **How a lecturer is matched.** `LecturerRegistry` stores email and an optional department. `Lecturers.ProfessionId` is required, and onboarding never collects a profession. Decide where profession comes from, and what happens when the registry row has no department.
- **One role per user.** The schema allows a single `RoleId`. The UI label `teacher` maps to canonical `lecturer`. Decide whether a person who is both an alumnus and a lecturer can have one account, whether the role chosen at onboarding can change later, and what happens to the education row or the `Lecturers` row if it does.
- **When the check runs.** Registration sends only email, password, and name. Role is chosen later, on onboarding. Decide whether an account may exist before a registry claim, and which states exist (unverified, pending, rejected, active). For each state, decide whether that person can log in, appear in search, post, or message, and who approves a failed or missing match. No administrator role is defined; do not invent one silently.
- **Incomplete profiles are publicly reachable.** New users default to a public profile before onboarding finishes. Decide whether they are excluded from search and from `GET /users/{id}` until `onboardingComplete` is true.

## Authentication, recovery, and sessions

- **Second factor.** Settings expose a toggle, while the report calls for 2FA. Decide whether it is mandatory or optional, the method (app TOTP, email code, or other), how enrollment works, how a lost device is recovered, and whether turning it off requires the current password. Login must not issue a fully authenticated session before a required second factor succeeds.
- **Challenge rules.** The mock uses a fixed code, a 10-minute lifetime, 5 attempts, and a 60-second resend wait. Those are demo rules. Decide code length and entropy, expiry, attempt lockout, whether resend invalidates the previous code, and whether a new forgot-password request cancels the previous challenge. Routes for second-factor verify/resend and recovery resend are not mapped.
- **Account enumeration.** Decide whether an unknown email, a wrong password, a duplicate registration, and a deactivated account return the same HTTP status and the same user-visible message.
- **Recovery request body.** The pages require `challengeId`, then `recoveryToken`, then a reset bound to that proof. The HTTP adapter still posts `{email, code}` and `{email, code, newPassword}` and does not send `challengeId` or `recoveryToken`. Choose one contract. A reset must not succeed from the email address alone, and verifying a code must not authorize a later reset that only repeats the email.
- **Password policy.** The mock requires 8–128 characters, an ASCII uppercase letter, a digit, and a special character, and it keeps leading and trailing spaces. Production policy is open. Decide those rules, including whether the new password must differ from the current one. Password hashes, recovery secrets, and challenge material never appear in user DTOs.
- **Email change.** Decide whether the new address must pass the university allowlist and a fresh registry match, whether it needs its own verification code before it becomes the login address, and what happens to existing sessions, recovery challenges, and 2FA enrollment. The current password is required.
- **Session lifetime.** Access-token format and lifetime, refresh-cookie name, and `SameSite`, `Secure`, and `HttpOnly` flags are unspecified, as are rotation and reuse detection. Decide whether logout, password change, password reset, email change, deactivation, and deletion revoke only the current device or every session.
- **Cross-origin cookies.** The static site and the API are different origins (`python3 server.py` versus port 3004). Decide the allowed origin and CSRF protection for cookie calls (`/auth/refresh`, `/auth/logout`). There is no `/api` prefix unless one is added to both sides together.
- **Logged-out `/auth/me`.** The client accepts either a `null` body or a terminal 401. Return one of them, not both.

## Profiles, education, and media

- **Headline versus specialization versus institute.** The user DTO has `jobTitle` and a separate academic `specialization`. SQL has `Users.Specialization` plus a different specialization on each education row. Search matches the denormalized user fields, while graduation year is supposed to come from one chosen education or registry record. After the user edits education, those copies can diverge. Pick the canonical source for profile cards, search, and the professional headline.
- **Onboarding must not invent a degree.** Study years are year-only. The mock turns them into September–June dates and fills in a university and a bachelor degree the user never entered. Decide the stored value, how a master's or PhD alumnus is represented, and the rule that year-only input must not become a fabricated calendar day. Registry dates stay official full dates and stay distinguishable from profile dates.
- **Repeating onboarding.** The page is shown once, but nothing stops the API from being called again. Decide whether a second call updates the original education row or inserts another, and whether the lecturer row is created in the same transaction as the profile update. A chosen photo must be stored successfully before onboarding is marked complete; skipping the photo is allowed.
- **Free text versus lookup ids.** Education and onboarding submit display names. SQL expects `UniversityId`, `DegreeId`, `InstituteId`, and `SpecializationId`. Decide who may create a lookup row, how near-duplicate Armenian names are merged, what `IsVerified` changes in the product, and whether a user can rename a shared row.
- **Reference lists.** Institute, department, sphere, post type, and forum major options are fixed labels in the client. There is no reference API, and forum majors have no table. Persist stable codes (`job`, `internship`, `training`, `informatics`, and the other listed codes). Do not use a localized `Name` as the code.
- **Date precision.** Profile dates are `YYYY-MM`, onboarding sends a year, SQL stores `DATE`, and `DATETIME2` defaults to server local time via `SYSDATETIME()`. The API contract requires UTC timestamps. Define the conversion both ways. A null end date means ongoing; decide whether several ongoing education rows are allowed. Reject an end that precedes the start.
- **Certificates.** The URL column is `NVARCHAR(255)` in the creation script and `NVARCHAR(MAX)` on the diagram. The client expects `logo`; the table has no logo column. Decide whether the URL is optional, its maximum length, the allowed schemes (`http` and `https` only, as the client checks), and whether the logo is an upload, a default, or dropped from the DTO.
- **Biography.** Length is not in the written limits. Onboarding requires it; a later profile save can clear it. Decide the maximum (SQL `About` is `NVARCHAR(MAX)`) and treat biography as plain text, not HTML.
- **Uploads.** Allowed types are PNG, JPEG, WebP, and GIF, nonempty and at most 5 MiB. The client checks the browser-reported type only. Decide magic-byte validation, replacement and deletion of the previous object, whether the file URL remains fetchable after the profile is closed, and which placeholder is used when avatar or cover is empty. Browser preview URLs are not server assets.
- **Work experience.** `WorkExperience` exists in SQL and has no page, editor, or route. Confirm that it is out of this version, including data export.

## Privacy

- **Closed profile.** The mock hides the person from search and from the profile page, but leaves their posts, topics, replies, and comments visible with an author. Decide whether that author's name is still shown, whether it still links to the profile, and whether a direct `GET /users/{id}` for a closed profile is 404 or 403. 404 avoids confirming that the account exists.
- **Email disclosure.** `showEmail` has no column. It is independent of the login identifier. Define the four cases: public profile with email hidden, public profile with email shown, closed profile, and the owner viewing themselves. Search results and public profile reads must follow the same rule. `passwordChangedAt` is on the user DTO; keep it on the owner projection only unless a public display is an explicit decision.
- **Blocks outside chat.** Blocking is specified for direct messages. It is not specified for search results, profile views, or forum replies. Decide each one.

## Posts and forum

- **Which fields are required.** The UI requires a title; SQL allows a null title. Sphere may be empty in the client and is not checked against `programming`, `engineering`, `data-science`, and `marketing`. Category must be `job`, `internship`, or `training`. Confirm that sphere is optional, reject unknown category and sphere codes, and reject a blank title.
- **Comments embedded in a post.** `GET /posts` is specified with a `comments` array, and `GET /posts/{id}/comments` also exists. Decide whether a feed post contains the full thread, a short preview, or only a count, and define sort order and page size. Do not build durable ids from array positions.
- **Writes the UI does not show.** Comment edit/delete and topic edit/delete exist as client services and have no buttons. Decide whether those operations are in this version. Deleting a post removes its comments; deleting a topic cascades to replies and likes, including other people's replies. Confirm that consequence, or define a different retention rule.
- **Rich-text allowlist.** Both docs require a narrow allowlist and do not list it. Freeze the set the client already uses: `p`, `br`, `b`, `strong`, `i`, `em`, `u`, `ul`, `ol`, `li`, `a`, `div`, `h2`, `h3`, `blockquote`. Links may be `http`, `https`, or `mailto`. No `style`, `class`, event handler, or other attribute. The server must sanitize; the browser check is not enough. The 20,000-character limit counts visible text, not raw markup. Reject whitespace-only markup such as `<p><br></p>`. Titles, names, and comments stay plain text even when rendered next to HTML.
- **Forum classification.** Major codes (`informatics`, `mechanics`, `electronics`, `civil`, `energy`, `management`) have no foreign key. Decide whether they are their own lookup, or are actually specializations or spheres. Topic create requires one of these codes.
- **Sort and likes.** Newest, oldest, and popular need a stable tie-break. The mock orders popular by like count, then timestamp, then id. Popular applies to replies, not to the topic list. One user likes a reply at most once, and unliking removes that row. Decide whether liking your own reply is allowed. The per-reply “Պատասխանել” control only moves focus to the composer; it must not create a parent reply.
- **Missing topic id.** A topic URL without an id currently selects topic 1. With real ids, that request should be an error, not a default record.
- **Moderation.** There is no moderator role, report action, or hidden-content state. Decide whether anything other than owner delete can remove a post, topic, or reply. The report describes discussions more broadly than the career forum shown in the UI; resolve that scope before adding moderation rules.

## Search

- **Filters have to be server parameters.** The client sends only `q` and then filters institute, specialization, and graduation year on the returned array. That is wrong as soon as the server returns a page instead of every user. Define the parameter names, whether filters combine with AND, the sort, the page size, and the result of an empty query (no rows, or the first page).
- **Match rules.** The mock uses a case-insensitive substring over name, headline, and specialization. Armenian collation, punctuation, and partial tokens are undefined. Graduation year must come from one identified education or registry record when the person has several educations. Define how a lecturer with no graduation year behaves when a year filter is set.
- **Who is returned.** Joins must not emit the same person twice. Decide whether the caller, incomplete profiles, deactivated users, and blocked users are included. Return a public card (durable id, name, avatar, academic fields, profile link), not a full user object that may contain email or `passwordChangedAt`. Official registry rows are not a directory.

## Chat

- **Encryption, before the message table is final.** `EncryptedContent` implies ciphertext. The UI searches message text, shows previews, and export includes sent message bodies as plaintext. End-to-end encryption conflicts with server-side search, previews, and that export. Server-managed encryption at rest does not. A column name and the commented-out key tables are not a protocol. If end-to-end encryption is chosen, algorithm, version, nonce, authentication tag, key distribution, rotation, recovery, multi-device access, and attachment encryption all have to be specified, and the export and search behavior above have to be rewritten.
- **Direct rooms.** Decide that a pair of users shares one room, that self-chat is rejected, and what happens to that room after block, unblock, hide, and account deletion. The mock reuses the pair and makes a room with one remaining participant read-only (`closed`).
- **Groups.** Group rooms render, and the seed data contains one. There is no create, invite, leave, rename, or role control. Either groups are not creatable in this version, or specify the member limit, the owner, and a single transaction for membership changes and message writes.
- **`closed` and `blocked` are different.** `closed` means the room has fewer than two participants; it is not a stored flag. The conversation `blocked` flag means “I blocked this person,” not “they blocked me.” Sends are rejected if a block exists in either direction. Define all four cases (I blocked them, they blocked me, both, neither): whether the composer is disabled, whether the other person's block is revealed, and the error text. In a group, decide whether a block against one member rejects every send or only directs. Group block controls are not in the UI.
- **Hide versus delete.** The menu label is “delete conversation.” The behavior is a per-user hide plus a timestamp cutoff. A later incoming message shows the room again, without the hidden history. It does not delete the other participant's copy. Confirm this, or define a true delete.
- **History window.** Decide whether a participant sees messages from before they joined and after they left. `JoinedAt` does not answer that.
- **Read state.** Unread count is messages from other people after this viewer's last read time. Opening the room clears it. There is no delivered, read-receipt, or presence model. Show only the unread badge unless those states are actually stored. Do not claim online or delivered.
- **Mute.** Per-room mute is separate from the account-level direct-message preference. Decide whether mute suppresses email only, the unread badge, or both.
- **Attachments and message shape.** One optional image per message, using the same PNG, JPEG, WebP, GIF, and 5 MiB rules. Empty text is allowed only when a file is present. Text is limited to 5,000 characters. Decide storage, who can fetch the file URL, and how the original filename is displayed. There is no message edit or unsend.
- **Delivery.** No websocket, SSE, or polling contract exists. Local mock events are not a server protocol. Define event types, ordering, how a reconnect fills the gap, and an idempotency key so a retried send is not stored twice. In-room text search currently loads the visible thread and filters it in the browser; define a bound before history can grow without a limit.

## Settings, notifications, and account lifecycle

- **Russian.** The UI offers `hy`, `en`, and `ru`. The SQL seed has `hy` and `en` only. Storing `ru` does not translate the interface or user content. Decide whether `ru` is a legal `Language` code. User-written posts and messages stay in the language they were written in.
- **Notification defaults.** `UserNotificationSettings` is optional, and its bits are nullable. Decide the meaning of a missing row and of NULL (the mock default is all four enabled, profile public, email hidden, 2FA off, language `hy`). “New listing” does not say which posts qualify: every post, or only a matching sphere or major. Forum notifications are replies to topics the user authored, not a subscription list. Decide whether `emailEnabled: false` stops email only, whether room mute and block suppress delivery, and whether users are notified about their own posts, comments, and replies. No delivery table, template, or scheduler exists; preferences alone do not send anything.
- **Deactivation.** The mock requires the current password, ends the session, hides the profile, leaves published posts in place, and reactivates the account on the next successful login. Confirm that login-to-reactivate is intentional, and what the other person sees in an existing chat while the account is deactivated.
- **Deletion.** “Delete the account and all data” is not what the foreign keys do. Comments, topics, replies, likes, and sent messages reference the user without cascade, so a physical delete can fail; cascading them would remove other people's replies under that user's topics. For each of these, decide delete, anonymize as a deleted user, or retain: posts, comments on other people's posts, topics, replies, likes, sent messages, direct rooms, group membership, media files, education, certificates, and the registry claim. Also decide whether the email address and diploma can be registered again, whether deletion has a grace period, and that export-before-delete is or is not required. Password confirmation is required. The mock's surviving direct room becomes read-only; confirm or replace that rule.
- **Export.** Include the caller's profile, settings, posts, comments, topics, replies, sent messages, and own media. Exclude passwords, tokens, challenges, and other participants' message bodies. Decide whether the response is synchronous JSON or a generated file, and the size limit. End-to-end encryption would remove plaintext messages from this file. Clearing local browser data is not a server route.

## API contract

The client will not infer the items below. Paths that are not mapped fail visibly as `UNSUPPORTED` and must not be guessed.

- **One success shape.** The client accepts a bare DTO, `{data: DTO}`, and `{success: true, data: DTO}`. Emit one. Lists are JSON arrays, including an empty list. There is no pagination envelope. Deletes: the client ignores the body, so return an empty success.
- **Errors.** Use 400 for validation, 401 for unauthenticated, 403 for forbidden, 404 for not found, and 409 for conflict. The client displays `message` as-is, so that string must be Armenian user text, or the client must grow a code-to-text map. Define `fieldErrors` as either a field-to-string map or a field-to-string-array map, and use it consistently. 413, 422, and 429 are undefined; add them only together with client handling. A retried 401 after refresh, or a failed refresh, clears the access token. Auth calls must not enter the refresh loop.
- **Partial update versus replacement.** Profile intro and settings sends are partial. Education and certificate updates replace the mutable fields. Decide, for each write, whether an omitted field is left unchanged or cleared. Reject unknown fields. The authenticated user is taken from the session, never from `userId`, `author`, or a timestamp in the body.
- **Routes still missing.** Second-factor verification and resend; recovery resend; forum reply create and like; every chat operation; settings read/update; email change; password change; deactivation; deletion; export; eligibility; reference data. Service meaning exists. Method, path, and body do not. Do not attach account deletion to `DELETE /users/me` until the retention rules in this document are decided. `GET /users/{id}/posts` is the identified-user post read. `PUT /users/profile` is onboarding multipart; `PUT /users/me` is the profile intro. Do not merge them.
- **Pagination and client-side filters.** Category, sphere, forum major, and search filters run on the full array the server returned. A page envelope, or a partial list, will silently drop matches until the client and the query parameters are updated together.
- **Ids, retries, and concurrency.** Ids are opaque strings. Sequential integers are guessable. There is no ETag, version, or idempotency key. A retried create can duplicate a post, comment, education row, certificate, or message. Define the key for those writes, or accept last-write-wins and duplicate creates as the contract.
- **Limits to reconcile with SQL.** Names 100 characters. Titles 255. Rich text 20,000 visible characters. Messages 5,000. The written spec gives comments the same 5,000 limit; the mock enforces 2,000 on create and update. Pick one. Certificate URL length, biography length, and lookup-name length still disagree with the declared SQL widths (`Users.Specialization` is 150, education name fields are 255, certificate URL is 255 or MAX). Blank `NVARCHAR` values are not rejected by `NOT NULL`.

## Confirm these are out of scope

Do not implement these unless a later decision adds them:

- University events, venues, RSVP, and attendance. `events.html` is the announcement feed.
- Work-experience editing or API.
- Help-form submission and any ticket store. The form tells the user that submission is unavailable.
- Tutorial upload, playback, or a video catalog. The page reports that video is unavailable.
- An administrator, moderator, or import UI. Alumni import stays the offline `import_alumni.py` script until provenance, correction, and revocation are specified, including what happens when a registry row disappears after an account has claimed it.
- Nested forum replies, topic subscriptions, and bookmarks.
- Delivered, read, and online indicators in chat.
- Translated UI catalogs. A saved language code is not a translation.
