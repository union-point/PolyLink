# PolyLink backend․ ուսումնական ուղեցույց

Ուղեցույցը նկարագրում է repository-ում իրականացված backend-ը։ Կոդում առկա հնարավորությունը դեռ չի նշանակում, որ այն միացված է կոնկրետ աշխատող համակարգում։

## 1. Ընդհանուր գաղափարը

Backend-ը հավելվածի սերվերային մասն է․ ընդունում է frontend-ի HTTP հարցումները, ստուգում է օգտատիրոջ ինքնությունն ու իրավունքները, կատարում է բիզնես կանոնները և աշխատում է տվյալների բազայի հետ։ PolyLink-ում այն սպասարկում է գրանցումը, մուտքը, օգտատերերի որոնումը, հաղորդագրությունները, խմբերը, ֆորումը, հայտարարությունները, կարգավորումները և հաշվի կյանքի ցիկլը։

Սա մեկ Spring Boot հավելված է՝ ըստ գործառույթների բաժանված մոդուլներով։ Այսինքն՝ մոդուլային մոնոլիտ է․ `auth`, `chat`, `forum` և մյուս փաթեթները առանձին microservice-ներ չեն։

```text
Բրաուզեր / frontend
        │ HTTP հարցում, հիմնականում JSON
        ▼
Անվտանգության սահման՝ origin, հարցման չափ, նույնականացման ստուգումներ
        ▼
Controller → Service → JdbcTemplate / SQL → SQL Server
                 │
                 ├── SMTP՝ նամակների ուղարկում
                 └── OpenBao Transit՝ բանալիների վերականգնման պաշտպանություն
```

Պատասխանը հակառակ ուղղությամբ վերադառնում է frontend-ին։ Ֆայլերի որոշ գործողություններ օգտագործում են բինարային տվյալներ։

## 2. Հիմնական տեխնոլոգիաները և դրանց դերը

| Գործիք | Ինչի համար է օգտագործվում |
| --- | --- |
| Java 25 | Backend-ի ծրագրավորման լեզուն է։ |
| Spring Boot 4.1.1 | Կազմակերպում է հավելվածի մեկնարկը, բաղադրիչների ստեղծումն ու կապակցումը, կարգավորումները և HTTP սերվերի աշխատանքը։ |
| Spring Web MVC | Controller-ների միջոցով URL-ները կապում է Java մեթոդների հետ, մշակում հարցումներն ու պատասխանները։ |
| Spring Security | Սահմանում է հասանելի երթուղիները և անվտանգության ընդհանուր կանոնները։ Նախագծի սեփական identity/session տրամաբանությունը լրացնում է այն։ |
| Spring JDBC / JdbcTemplate | Կատարում է SQL հարցումները և արդյունքները փոխանցում Java կոդին։ |
| TransactionTemplate | Մի քանի փոխկապակցված փոփոխություն կատարում է մեկ transaction-ի մեջ։ Սխալի դեպքում ամբողջ գործողությունը կարող է հետ շրջվել։ |
| Microsoft SQL Server և JDBC driver | SQL Server-ը պահում է տվյալները, իսկ driver-ը Java հավելվածին միացնում է բազային։ |
| Flyway | Պահպանում և կիրառում է բազայի կառուցվածքի հերթական փոփոխությունները՝ migration-ները։ |
| Spring Mail / SMTP | Ուղարկում է հաստատման, վերականգնման և նախատեսված ծանուցումների նամակները։ |
| OpenBao Transit | Պաշտպանում է բանալիների վերականգնման համար պահվող սերվերային պատճենը։ |
| Argon2id / Bouncy Castle | Մասնակցում են նույնականացման գաղտնիքի անվտանգ հեշավորմանը։ Հեշը գաղտնիքի միակողմանի ստուգիչ ներկայացումն է։ |
| OWASP Java HTML Sanitizer | Մաքրում է թույլատրվող հարուստ տեքստը վտանգավոր HTML-ից՝ XSS-ի ռիսկը նվազեցնելու համար։ |
| Maven և Maven Wrapper | Կառավարում են կախվածությունները, կոդի հավաքումը, թեստերն ու executable JAR-ի ստեղծումը։ |
| Spring Boot Actuator | Տրամադրում է առողջության ստուգման `/actuator/health` հասցեն։ |

`pom.xml`-ում առկա է նաև Spring Data JPA կախվածություն, բայց հիմնական բիզնես տվյալների հասանելիությունը կառուցված է բացահայտ SQL/JDBC-ի վրա։ Չպետք է ներկայացնել համակարգը որպես JPA entity/repository ճարտարապետություն։ Բրաուզերի libsodium-ը հաճախորդի գաղտնագրության գործիք է, ոչ Java backend-ի գրադարան։

## 3. Կոդի շերտերը և մոդուլները

**Controller**-ը HTTP մուտքի կետն է․ կարդում է պարամետրերը և փոխանցում գործողությունը համապատասխան ծառայությանը։ **DTO**-ն հարցման կամ պատասխանի տվյալների ձևաչափն է։ **Service**-ը ստուգում և իրականացնում է գործառույթի կանոնները։ Տվյալների հասանելիության SQL-ը հաճախ հենց ծառայությունների ներսում է․ պարտադիր առանձին repository շերտ չկա։

| Փաթեթ | Պատասխանատվություն |
| --- | --- |
| `auth` | Գրանցում, համալսարանական գրանցամատյանով համապատասխանության ստուգում, email հաստատում, մուտք, session-ներ և գաղտնաբառի փոփոխություն։ |
| `keyvault` | Գաղտնագրված հաճախորդային բանալիների պահպանում և OpenBao-ի հետ աշխատանք։ |
| `recovery` | Հաշվի և գաղտնագրված պատմության հասանելիության վերականգնման ընթացք։ |
| `chat` | Անձնական և խմբային հաղորդագրություններ, կցորդներ, անդամակցություն, կարդացածի ու արգելափակման վիճակ, հաշվի կյանքի ցիկլ։ |
| `forum` | Կատեգորիաներ, թեմաներ, պատասխաններ, խմբագրում, ջնջում և հավանումներ։ |
| `posts` | Հայտարարությունների և մեկնաբանությունների API։ |
| `search` | Օգտատերերի որոնում, ֆիլտրեր և հասանելի պրոֆիլների ներկայացում։ |
| `settings` | Գաղտնիության ու ծանուցումների կարգավորումներ, email-ի փոփոխություն և տվյալների արտահանում։ |
| `database` | Բազայի կառուցվածքի ստուգման ու migration-ների գործարկման հրամաններ։ |
| `config` | Անվտանգության ընդհանուր կարգավորում։ |

Spring-ի dependency injection-ը անհրաժեշտ բաղադրիչը փոխանցում է այն օգտագործող դասին։ Օրինակ՝ ծառայությունը ստանում է `JdbcTemplate`, որպեսզի բազայի հետ կապը ինքնուրույն չստեղծի յուրաքանչյուր հարցման ժամանակ։

## 4. Ինչպես է անցնում հարցումը

Օրինակ՝ օգտատերը ստեղծում է ֆորումի թեմա։

1. Frontend-ը ուղարկում է HTTP հարցում՝ տվյալներով և նույնականացման համապատասխան տվյալներով։
2. Ստուգվում են հարցման աղբյուրը, չափը և API-ի հասանելիությունը։
3. Controller-ը հարցումը փոխանցում է ծառայությանը։
4. Ծառայությունը ստուգում է օգտատիրոջը, բովանդակությունը, կատեգորիան և գործողության իրավունքը։ Հեղինակը որոշվում է հաստատված ինքնությունից։
5. SQL գործողությունները կատարվում են transaction-ի ներսում, երբ պետք է միասին պահպանել մի քանի կապված փոփոխություն։
6. Backend-ը վերադարձնում է արդյունքը կամ սխալի պատասխան։ Frontend-ը թարմացնում է ցուցադրումը։

Բազայի foreign key-ը ստուգում է կապվող գրառման գոյությունը, բայց չի ապացուցում, որ հարցումն ուղարկող օգտատերը դրա սեփականատերն է։ Այդ ստուգումը ծառայության պարտականությունն է։

## 5. Գրանցում, մուտք և անվտանգություն

Գրանցումը պարզապես անուն և գաղտնաբառ պահելը չէ։ Պահանջվում են համալսարանական թույլատրելի email, պահպանված պրոֆիլ, ընտրված դերին համապատասխան գրանցամատյանի եզակի համընկնում և email-ի հաստատում։ Գրանցման սահմանափակ session-ը դեռ լիարժեք հաշվի իրավունքներ չի տալիս։

Բրաուզերը գաղտնաբառից ածանցում է մուտքի և բանալիների փաթեթավորման նյութը։ API-ն օգտագործում է `loginSecret` և ածանցման տվյալներ․ սովորական `{email, password}` պայմանագիրը չի նկարագրում իրական մուտքը։ Սերվերը պահում է պաշտպանված ստուգիչ, ոչ բաց գաղտնաբառ։

Մուտքի համար օգտագործվում են սերվերում կառավարվող opaque access credential-ներ և refresh մեխանիզմ։ Դրանք JWT անվանելը սխալ է։ Access credential-ը frontend-ում պահվում է հիշողության մեջ։ Cookie-ով նույնականացման դեպքում կիրառվում են session-ին կապված CSRF ստուգումներ։ Origin սահմանափակումը պաշտպանում է փոփոխող հարցումների սահմանը, բայց չի փոխարինում օգտատիրոջ իրավունքների ստուգմանը։

Ընտրովի երկրորդ գործոնը email-ով հաստատումն է։ Գաղտնաբառի փոփոխությունը նախատեսված է գաղտնագրված պատմության հասանելիությունը պահպանելու և մյուս սարքերի session-ները չեղարկելու համար։ Rate limit-ները սահմանափակում են կրկնվող փորձերը։

Spring Security-ի որոշ երթուղիների `permitAll()` նշումը չի նշանակում, որ բիզնես գործողությունը բաց է բոլորի համար․ նույնականացումն ու թույլտվությունները ստուգվում են նաև նախագծի սեփական շերտերում։

## 6. Հաղորդագրություններ և գաղտնագրում

Հաղորդագրությունների տեքստն ու պատկերները գաղտնագրվում են բրաուզերում։ Backend-ը պահում է գաղտնագրված բովանդակությունը և ստուգում ուղարկողի անդամակցությունը, բանալու տարբերակը, հաղորդագրության կառուցվածքն ու չափը։ Այն նաև գիտի գործառույթի համար անհրաժեշտ մետատվյալները՝ օրինակ սենյակն ու հաղորդագրությունների հերթականությունը։

- Սենյակի հաջորդական համարները տալիս են կայուն հերթականություն։
- Cursor-ով էջավորումը թույլ է տալիս պատմությունը վերցնել մասերով։
- Idempotency-ն թույլ է տալիս նույն ուղարկումը կրկնել կապի խափանումից հետո՝ առանց նոր կրկնօրինակ ստեղծելու։
- Խմբի անդամակցության ժամանակային միջակայքերը սահմանափակում են հասանելի պատմությունը։
- Կցորդների ներբեռնումը նույնպես պահանջում է հասանելիության ստուգում։

Ծանուցումների ընթացիկ թարմացումներն օգտագործում են պարբերական HTTP հարցումներ՝ polling։ Չպետք է միայն «չաթ» բառից ենթադրել WebSocket-ի կիրառում։

Վերականգնումը վստահում է հարթակին․ OpenBao Transit-ը պաշտպանում է վերականգնման պատճենը, և հաստատված վերականգնման ընթացքը կարող է վերականգնել բանալիների հասանելիությունը։ Ուստի ճիշտ չէ պնդել, թե հարթակը ոչ մի պայմանով չի կարող աջակցել բանալիների վերականգնմանը։

## 7. Բազա, transaction-ներ և migration-ներ

SQL Server-ում բիզնես տվյալներից բացի կան `auth`, `keyvault`, `messaging` ոլորտների կառուցվածքներ։ Transaction-ը կապված փոփոխությունները պահում է որպես մեկ ամբողջություն։ Օրինակ՝ գործողության տվյալը և դրա հետ կապված ծանուցման իրադարձությունը պետք է հետևողական մնան։

Աղբյուրներում կան Flyway V1–V21 migration-ներ։ Դրանք հերթով զարգացնում են սկզբնական կառուցվածքը՝ ավելացնելով նույնականացում, հաղորդագրություններ, կարգավորումներ, ֆորում և հայտարարություններ։ Ավելի ուշ migration-ները նաև հեռացնում են հնացած դաշտերը։

Հավելվածի մեկնարկը ինքնաբերաբար migration չի կատարում․ Flyway-ն ու SQL initialization-ը անջատված են։ `SchemaCommand`-ը նախատեսում է `inventory`, `upgrade`, `fresh` գործողությունները և պաշտպանում է անհամապատասխան կառուցվածքի դեմ։ Migration-ի և առօրյա աշխատանքի հաշիվների իրավունքները տարանջատված են։ Կոդում V21 ունենալը չի ապացուցում, որ աշխատող բազան արդեն V21 է։

`db/` պանակը մեքենային հատուկ տեղային նյութ է և ընդհանուր ենթակառուցվածքի աղբյուր չէ։ Այս ուղեցույցը բազայի տեղադրման հրահանգ չի սահմանում։

## 8. Այլ կարևոր վարքագիծ և սահմանափակումներ

Ֆորումն ու հայտարարություններն ունեն էջավորում և մուտքային տվյալների ստուգում։ Ֆորումում optimistic version-ը օգնում է նկատել հնացած տարբերակով խմբագրումը, իսկ կրկնվող ստեղծման ճանաչումը՝ կանխել կրկնօրինակները։ Բովանդակության մաքրումը նվազեցնում է վնասակար HTML-ի կատարումը բրաուզերում։

Որոնումը և պրոֆիլի պատասխանը հաշվի են առնում տեսանելիության կարգավորումները։ Որոնումը email չի բացահայտում։ Փակ պրոֆիլը կարող է գտնվել որոնմամբ, բայց ամբողջ պրոֆիլի բացումը սահմանափակվել։

Identity-ն սկզբնական կարգավորումներով միացված է, իսկ messenger-ը, forum-ը և posts-ը ունեն առանձին միացման դրոշակներ և սկզբնական վիճակում անջատված են։ Իրական գործարկման համար անհրաժեշտ են համապատասխան արտաքին ծառայություններ, գաղտնի կարգավորումներ և բազայի ճիշտ տարբերակ։

Ընդհանուր պրոֆիլի, կրթության, վկայականների և մեդիայի փոփոխման ամբողջական API-ները դեռ իրականացված չեն։ Գրանցման avatar-ը առանձին իրականացված հնարավորություն է։ Frontend-ում գործողության առկայությունը չի ապացուցում համապատասխան backend API-ի գոյությունը։

## 9. Դասախոսի հնարավոր հարցերը

**Ի՞նչ ճարտարապետություն ունեք։** Մոդուլային մոնոլիտ՝ HTTP controller-ներով, բիզնես ծառայություններով և բացահայտ SQL/JDBC հասանելիությամբ։

**Ինչո՞ւ է պետք backend, եթե frontend-ն արդեն ունի ստուգումներ։** Frontend-ը հնարավոր է շրջանցել։ Տվյալների ու իրավունքների վերջնական ստուգումը կատարում է սերվերը։

**Authentication-ը և authorization-ը ինչո՞վ են տարբերվում։** Առաջինը որոշում է՝ ով է օգտատերը, երկրորդը՝ ինչ գործողություն կարող է անել։

**Հեշավորումն ու գաղտնագրումը նո՞ւյնն են։** Ոչ։ Հեշը միակողմանի ստուգիչ է, իսկ գաղտնագրումը նախատեսում է ճիշտ բանալիով սկզբնական տվյալների վերականգնում։

**Ինչո՞ւ է պետք transaction։** Որպեսզի կապված փոփոխությունները հաստատվեն միասին կամ ձախողման դեպքում հետ շրջվեն։

**Ինչո՞ւ են պետք migration-ներ։** Որպեսզի բազայի կառուցվածքի զարգացումը լինի հերթական, վերահսկելի և տարբեր միջավայրերում վերարտադրելի։

**Օգտագործո՞ւմ եք Hibernate/JPA՝ տվյալները պահելու համար։** Կախվածությունները կան, բայց իրականացված բիզնես մոդուլները հիմնականում աշխատում են JdbcTemplate-ով և SQL-ով։

**Ի՞նչ է պահվում հաղորդագրության համար։** Գաղտնագրված բովանդակություն և աշխատանքի համար անհրաժեշտ մետատվյալներ։ Բաց տեքստը պատրաստվում ու կարդացվում է հաճախորդում։

**Կրկնված HTTP հարցումը միշտ նոր գրառո՞ւմ է ստեղծում։** Համապատասխան գործողություններում idempotency/deduplication-ը ճանաչում է կրկնությունը։ Սա ինքնաբերաբար բոլոր endpoint-ների հատկությունը չէ։

**Ինչպե՞ս է ստուգվում backend-ը։** Maven-ի ստուգումները ներառում են ձևաչափը, առանց բազայի թեստերը և JAR-ի հավաքումը։ Առանձին integration/acceptance ստուգումները պահանջում են SQL Server և համապատասխան արտաքին ծառայություններ։
